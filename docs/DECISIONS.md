| D44 | `BaseViewModel`'s defaults | The loading overlay becomes **opt-in** — `loading = overlay()`, or `overlay(message)` to word it — because 24 of the 32 call sites in the app switched it off, and a default three call sites in four override is not a default. `loadingMessage` goes with it: a wording parameter separate from the switch could be set on a call that showed no overlay to put it on. `initialState` **stays nullable**. The measurement that decided the second half: three of the four screens that pass `null` have a natural empty state, and the product detail screen does not — its state holds a `Product`, which has no honest empty value, so a non-null envelope would move the null into the feature's own `@Immutable` state class, where `Screen()` no longer guards it and every preview and golden has to render it. That is the same null one level down, unguarded. What the null half was really for — an update arriving before the first state being dropped in silence, which is the shape of the bug A1X4 fixed by hand — is fixed directly instead: `updateData` is now a member of `BaseViewModel` that logs that case. Taken in B0X1 |

| D51 | `AppTextField`'s API | **Keeps `value` / `onValueChange`** and gains what it was missing: `imeAction`, `onImeAction` and `contentType`. Rebuilding on `TextFieldState` was the recommendation and is wrong for this template: a `TextFieldState` is mutable and observable, so the field's text cannot live in an `@Immutable` `XState` — it moves into the composable, and with it the validation every form view model here does on change. That is the one thing an MVI template exists to demonstrate not doing. Revisit when Compose's own guidance for a state-hoisted architecture settles; the missing parameters were the actual defect and cost three lines. The two size enums are folded in the same change: `ControlSize` is the one scale, and `ButtonSize`'s taller metrics become a private lookup inside `AppButton` — the goldens are byte-identical afterwards, which is what proves the fold changed nothing. Taken in B1U2 |
| D52 | Where the gallery's list comes from | **Hand-written, and checked.** `ComposablePreviewScanner` was the recommendation and does not survive contact: it is a classgraph-based scanner built for a JVM test classpath, and the gallery ships in `dev` and `staging` (D16), so it would have to run on a device. The deeper reason is that it would make the gallery worse — an entry carries several labelled variants and live, interactive demos, and a `@ComponentPreview` renders one fixed arrangement, so generating from previews would trade 46 rich entries for 46 thin ones. What was actually missing was enforcement: `create_component.py` now writes the starter entry and `doctor.py`'s `check_gallery_lists_every_component` fails on a component with none, or on an entry naming a component that does not exist. The brief's premise that two components were already missing was wrong — the gallery was complete; it was just complete by luck. `AppScaffold` and `ControlSize` stay out for the reasons the catalogue's own KDoc gives. Taken in B1U3 |
| D43 | The `staging` flavor | **Kept, alongside `dev` and `prod`.** It costs two small source-set files and one line in `ProjectConfig.Flavor`; the pull-request gate only compiles its Kotlin, not assembles it, so the surface that once justified cutting it is gone. | D53 | Where the data-source interface lives | **Kept, and two got a fake.** Deleting the ten interfaces would make `create_datasource.py` simpler and the data layer thinner, but it also removes the only seam a network or file-system failure can be injected through without a real client or a real filesystem — and the fakes are the cheaper half of that argument, so wrote them instead of deleting what they'd replace. Picked the two data sources with a real failure branch: `RemoteCatalogDataSource` (an HTTP call, mapped through `HttpErrorMapper`) and `AvatarDataSource` (a file copy that can fail on a revoked URI). `FakeRemoteCatalogDataSource` ships as available `testFixtures` infrastructure — `DefaultCatalogRepositoryTest` deliberately keeps its own `MockEngine` because cache-then-network is the thing *that* test asserts, so faking the network there would defeat it; the fake is for a narrower test that wants the failure without one. `FakeAvatarDataSource` got an immediate consumer: `DefaultProfileRepositoryTest`, which did not exist before this task — `DefaultProfileRepository` had no test at all. Both fakes needed AGP's `testFixtures` source set turned on for an Android library module, which the plain `java-test-fixtures` Gradle plugin cannot do (it collides with a configuration AGP already owns) — a new `convention.android.library.testfixtures` plugin does it instead, stacked alongside each module's existing convention plugin. `check_repository_depends_on_interface` needed no change; it already passed. Taken in B2P2 |
| D45 | The baseline profile | **Cut.** `:baselineprofile`, `convention.android.test` (its only consumer) and both plugin aliases are gone, along with the committed profile and the now-unused instrumentation libraries. Measured before deciding, without a device — none is attached in this environment, and no CI job ever ran the generation either, which is itself part of the finding: nothing has regenerated this profile since it was first committed. What could be measured is whether the committed `devRelease` profile does anything for `prodRelease` if pointed at it directly, since each flavor's R8 pass renames classes independently: built both bundles, and copying the profile to where AGP's native `src/main/baselineProfiles/` convention picks it up for every variant grew `prodRelease`'s embedded `baseline.prof` by 10 bytes out of roughly 9,900 — the recorded rules reference `devRelease`'s own obfuscated names and essentially none of them match `prodRelease`'s independently-renamed classes. A correct fix needs either a same-build mapping-rewrite between the two variants' R8 output or a separate device-generation run per flavor, well past what a two-plugin, one-consumer dependency should cost, and the benefit is unverifiable here regardless: this is a template with no startup-heavy real work to compile ahead of time, and the shipped build has carried none of this since v1.0 with nobody noticing. `docs/ai/DEPENDENCIES.md` loses its baseline-profile row. Taken in B2H2 |
| D58 | How many plans may be open | **Exactly one is open; the rest queue as `draft` or `paused`.** A third state was the cheaper half of the problem: release D had to run before B finished, and the alternative — two plans carrying `Status: open` — would have made "the plan whose header says `Status: open`" a question with two answers, forcing a tie-break rule into `/task`, `/release`, `PROCESS.md` and `CLAUDE.md` that none of them needs. `Status: paused` keeps that sentence true everywhere it is written, costs one word in a header, and `STATUS.md` keeps the paused release's board under its own heading so seventeen merged tasks are not cut to make room for nine unstarted ones. The second half: the 90–100 band sizes a **lane**, not a release — `ceil(60 ÷ 100)` is one lane either way, and "none is under 85" was written to stop a four-lane release being cut into five thin ones, not to set a floor under a release. A 60-point release is one lane under the floor, and the neighbouring rule — never pad a lane — says what the alternative would have cost. The budgets rise to 400 and 160 and move to `docs/README.md` alone, where they were already written a second time: a line count is a proxy for "this doc has started explaining itself", and the proxy was being enforced against the thing it stood for. Taken in D1P1 |

| D60 | The test-id vocabulary | **Stays closed, gains five content kinds, and the component-named tags are renamed — not widened to fit.** Measured first: 101 tags across the feature presentation modules, and the "nineteen violations" the task was written from is really 18, because 14 of the apparent offenders — `cart_item`, `categories_list`, `tripDetail_tabs` — are the vocabulary words `Item`, `List` and `Tab` in the lowercase a single-word element gets from camelCase. They always conformed; the reading of the rule was wrong, and any check has to fold case and plural before judging. Of the 18 that are real, 13 name a *kind of content* the existing thirteen words cannot express — an empty state, a skeleton, a card, a progress bar, a grouped section — and 5 name a *component*: `quantityStepper`, `budgetSlider`, `typeSegmented`, `advancedAccordion`. That split is the decision. Adding all eleven missing suffixes would take the list to 24 and turn a vocabulary into an inventory of `:core:ui`, which destroys the only property that makes it worth having: that you can guess `settings_permissionsButton` without opening the file. So the list gains `Card`, `Empty`, `Skeleton`, `Progress` and `Group` — kinds, not components, and each earns its place by describing something no existing word does — and the five component-named tags become `Field`, which is what a stepper, a slider, a segmented control and an accordion are when a form holds them. `cart_emptyState` and `trips_emptyState` lose the redundant `State`, and `tripWizard_reviewSummary` becomes a `Tile`. Eighteen words, and `check_test_id_vocabulary` enforces them. Taken in D1X4 |
| D61 | How many agents work a release | **One, lane by lane; two or three only when the owner writes it in the plan's `Agents:` line, for a release whose lanes are different kinds of work; never more, and never subagents or workflow scripts inside a session unless the owner asks for them by name.** The lane model was built for parallel agents — a lane was an agent-day, and the planner lowered the agent count until every lane was 85–100 points — and it cost what it saved: every agent is a full context, roughly 100k tokens read before its first edit, so four agents on a 380-point release paid 400k tokens of overhead to save a calendar day nobody had asked for. A lane is now a group of related work with a file set no other lane writes, as long as its work, worked in order by one agent; the disjoint file sets are what let a second agent take a lane if the owner wants the day back, so the Shared files table stays. The pull request follows the lane, not the task — one per lane, every task one commit on it, rebase-merged — so D17's invariant, `main` is one commit per task, stands with a fraction of the pull requests; D47 was the same shape for release A alone and is now the rule. Taken in E0P1 |

| D66 | How work is framed in time | **Sprints, and a sprint is a release.** The release machinery — ids, bands, lanes, the task loop, `/release` — works and nothing in it bounded a release in time: E ran until its backlog ran out, and the day's first question, "what can we do today", had no file to answer it. The owner asked for scrum. What it costs to adopt is one table in `PROCESS.md` mapping the vocabulary onto what already plays each part — the product backlog is `BACKLOG.md` § Next, planning is `/release draft` plus the owner opening it, the sprint goal and timebox are one `Sprint:` header line, the board is `STATUS.md`, review is `/release close`, the retrospective is the ratio — and what a second process beside the first would cost is two boards, two loops and a tie-break rule in every command. The timebox is one agent-day unless the owner writes otherwise, because 100 points is already the unit the bands are calibrated to. Field report (B3S2) is deleted from the backlog outright: it waited on purpose through two groomings and nothing has come to need its seams. Taken in F1P1 |
| D67 | Where the sprint is planned, and where it is read | **The sprint replaces the lane, a release collects sprints, the repository stays the truth, and a board artifact is the window on it.** Three things the owner asked for on 2026-09-15 and one constraint. *One sprint at a time:* the lane digit in a task id becomes the sprint digit — the pattern `^[A-Z][0-9][UXTHPS][1-9]$` does not change, so `doctor.py`, the changelog and every old id keep working — and a sprint is one branch, one pull request and one file, `plans/<letter><n>-<slug>.md`, with a name, a `When:` and a `Goal:` a person can read. Lanes existed so a second agent could take a file-disjoint group; a sprint's § Files table keeps that property per task, and D61's one agent makes the lane a digit nobody used. *A release is not a sprint:* `plans/<letter>.md` opens, collects done sprints, and ships as one changelog block when the owner says — after `/sprint close` the default is another sprint, never a tag, because a two-hour sprint is not a version. *Drafts are the queue:* the first `Status: draft` file listed in `STATUS.md` § Drafts is the next sprint by default. *The board can be read from anywhere:* a claude.ai artifact with a `db` store holds one document, `board/state`, written by `/board` from `scripts/board.py`'s output — a parser over `STATUS.md`, `BACKLOG.md`, `CHANGELOG.md` and `plans/` and nothing else. The constraint is the one this repository already lives by: a fact lives in one file. The artifact is never edited by hand and never written from the page; if it and `STATUS.md` disagree, `STATUS.md` is right and `/board` fixes the artifact. The alternative — the store as the truth and the docs generated from it — would put the sprint's briefs, which every task reads and every commit flips, behind a tool call. `BACKLOG.md` gains a group per line and a § DevOps section, so a board can be read by layer and an improvement sprint has somewhere to draft from. | D68 | Where the connectivity monitor lives | **The interface in `service/network`, the Android implementation in `:app`, and on `dev` the answer is the offline switch.** `service/network` stays the Kotlin/JVM module it is: making it an Android library to reach `ConnectivityManager` would cost every other consumer the JVM test speed and break `export_service.py`'s promise of a directory that compiles anywhere, for one class. The seam already exists — `HttpClientFactory` takes its engine as a parameter and `:app` hands it OkHttp or fixtures per flavor — so the monitor takes the same road: a port beside the engine, `AndroidConnectivityMonitor` in `:app`'s `src/main` where a Robolectric test can reach it, and a `connectivityMonitor()` per flavor source set beside `networkEngine()`. On `dev` the engine is in-process, so airplane mode means nothing to it; the one truth for "the server is down" there is `FixtureNetwork`, which the debug menu's switch already writes, so it implements the port itself and the banner follows the switch. The retry policy reads the same flow and gives up at once while offline: three tries on a device with no route are three identical failures and two seconds of backoff in front of an answer that was known before the first. The banner is `AppBanner`, not a toast (D63): nothing happened, something is so, and it stays until it is not. Taken in F1H1 |
