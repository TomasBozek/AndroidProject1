# Reusable architecture: service/core/{domain,data,ui} and core/di
<!-- Generated 2026-09-10 from the review agents' saved output. Evidence is path:line at commit 4e0d2fc. Not edited by hand; the ranked summary is ../REVIEW.md. -->

## Summary
The core is sound and closer to Now in Android than it looks: Outcome + DomainError is the same shape as NiA's sealed Result, Screen() is genuinely the only collector (0 collectAsStateWithLifecycle calls in feature/), BaseRepository.cached() is a tested offline-first combinator NiA hand-writes per repository, the Analytics/ErrorTracker seams mirror NiA's AnalyticsHelper/NoOp pattern, and doctor's service-isolation check holds (no feature/app import leaks into service/). The problems are proportion and defaults, not direction. BaseViewModel (452 lines) carries a lifecycle-aware observe mode that no ViewModel uses, a loading-overlay default that 21 of 38 call sites explicitly turn off, and a nullable `data` that every feature works around; the shell that every user sees most (loading overlay, error page, empty page, alert, permission rationale) is un-themed Material 3 living outside the design system and it replaces the whole screen including the top bar; and the one standard thing missing is any SavedStateHandle use, so typed input dies with the process. About 450 lines of service API (Outcome flow combinators, recover, executeAsFlow, 7 of 8 Formats roles, two UiCommands, AlertPayload, CredentialsError, displayMessage) have zero callers. Trim those, flip the defaults, and add the two missing standard pieces; do not replace the base class with a plain ViewModel — the sample shows the buffered navigation channel, the reference-counted overlay and the inline retry all earning their place.

## Problems (ranked by the reviewer)
### P1 · BaseViewModel: the overlay default is wrong for the sample, whileSubscribed has no caller, and nullable data is worked around everywhere

**high · over-engineered · effort M · confidence 0.85**

Three measured facts. (1) Of 38 execute/observe call sites in feature/, 21 pass `loading = {}` to switch the blocking overlay off, and four of them carry a comment explaining why the default is wrong here (CartViewModel:82, HomeViewModel:52, ProductDetailViewModel:60, SettingsViewModel:54) — a default that the majority overrides with an apology is the wrong default. (2) `observe(whileSubscribed = true)` plus `whileStateIsCollected()` (BaseViewModel.kt:276-377, ~100 lines with the grace-period dance) has 0 callers in feature/ or app/ and 6 tests (BaseViewModelTest.kt:359-444, ~86 lines); it landed as core.3 and nothing has needed it since. (3) `state: StateFlow<UiState<State?>>` makes every feature write `state.data?.copy(...)` — 9 such workarounds in feature ViewModels, 79 `.data!!`/`.data?.` in tests — and `updateData` silently does nothing while data is null (UiState.kt:29-38). That is a live race: ProductDetailViewModel:62-71 observes the favourite flag concurrently with load(); an emission that arrives before the product does is dropped, so the heart is stale until the next write. HomeViewModel:59-61 has the same pattern. The rest of the class (execute/observe, reference-counted overlay, Inline retry keyed by id, buffered channels, typed alert results) is used by the sample and is the right amount of base class — a plain ViewModel + extension functions would re-grow exactly this.

**Proposal.** Keep BaseViewModel; slim it. (a) Flip the default: `loading` defaults to no overlay, `loadingMessage`/overlay is opt-in (`loading = overlay()` or a `blocking = true` flag); delete the four explanatory comments. (b) Delete `whileSubscribed`/`whileStateIsCollected` and its 6 tests; if a socket or polling source ever appears, `stateIn(WhileSubscribed(5_000))` at the repository is the standard answer. (c) Make `initialState: State` non-null and express 'cannot render yet' as `ContentState.Loading` rendered by Screen() in place of content — `data` is then never null, `updateData` cannot drop an update, and the 9 workarounds and the ProductDetail race disappear. Also drop the unused `scope` parameter, `showUnexpectedErrorAlert`, `UiCommand.CloseApp`/`OpenBrowser` and `AlertPayload` (0 callers each) or move them to the backlog note.

Evidence: `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:208-217`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:276-377`; `service/core/ui/src/test/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModelTest.kt:359-444`; `feature/catalog/presentation/src/main/kotlin/com/example/androidproject1/feature/catalog/presentation/productdetail/ProductDetailViewModel.kt:62-71`; `feature/home/presentation/src/main/kotlin/com/example/androidproject1/feature/home/presentation/home/HomeViewModel.kt:52-63`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/state/UiState.kt:29-39`
### P2 · The screen shell (loading, error, empty, alert, permission rationale) is un-themed Material 3 outside the design system, and ContentState replaces the whole screen including its top bar

**high · inconsistent · effort M · confidence 0.8**

CLAUDE.md's rule is 'a feature composes components; it never draws' with no material3 and no dp literals, and 47 App* components exist to make that true. But the five composables a user sees on every load, failure, empty result, confirmation and permission prompt — ContentMessage, LoadingOverlay, StateAlertDialog, PermissionRationaleContent and Screen()'s Surface — are raw `androidx.compose.material3` with `32.dp`/`12.dp`/`16.dp` literals (ContentMessage.kt:36-37, LoadingOverlay.kt:29, PermissionGate.kt:84-85), because service/core/ui cannot see :core:ui. So the KSD theme covers the happy path and the M3 defaults cover everything else. Worse, Screen.kt:57-64 composes ContentMessage *instead of* the feature content, so an empty category (ProductsViewModel:43-47) or a not-found product loses its AppScaffold, title and Up control — which is why ContentMessage has to pad itself with safeDrawingPadding (ContentMessage.kt:34-35) and plausibly why qa.5 raised shell.8 ('every non-root screen carries an Up control'). Standard practice (NiA, the M3 guidelines) renders empty/error states inside the screen's scaffold, below the top bar.

**Proposal.** Give Screen() slots with defaults — `loading`, `alert`, `content: @Composable (ContentState, onAction) -> Unit` — and a `LocalScreenChrome` (or plain parameters wired once in AppNavHost) that :core:ui fills with KSD-themed implementations; the M3 versions stay as the portable fallback. Render the ContentState *inside* the feature content: pass it to the screen (`content(state, contentState, onEvent)`) or, simpler, have AppScaffold read it from a CompositionLocal and draw the empty/error body under its own top bar. Then the four service composables lose their dp literals by taking sizes from MaterialTheme only, and the design-system rule finally covers what users see most.

Evidence: `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/component/Screen.kt:54-64`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/component/ContentMessage.kt:31-63`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/component/LoadingOverlay.kt:23-34`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/permission/PermissionGate.kt:81-110`; `feature/catalog/presentation/src/main/kotlin/com/example/androidproject1/feature/catalog/presentation/products/ProductsViewModel.kt:43-47`
### P3 · No SavedStateHandle use anywhere: typed input and transient screen state do not survive process death

**high · missing-standard · effort M · confidence 0.7**

`lifecycle-viewmodel-savedstate` is on every presentation module's classpath (service/core/ui/build.gradle.kts:23) and `SavedStateHandle` appears in 0 main source files — only in two comments, one of which (BaseViewModel.kt:59-61) declares there is 'no SavedStateHandle detour'. That is correct for route arguments (Navigation 3 keeps the key in a rememberSaveable back stack) and wrong for everything else: the login email/password (LoginViewModel:18-21), the sign-up form, the search query (ProductSearchViewModel:39) and the checkout alert all live in a plain MutableStateFlow and are gone after 'Don't keep activities' or a background kill. Google's 'Save UI state' guide names SavedStateHandle as the day-one mechanism for exactly this, and NiA's ViewModels take it. qa.5 verified process death 'four deep' for navigation only. A user who typed an address, took a call, and came back to an empty form is the single most common process-death complaint in a product app.

**Proposal.** Add an optional hook to BaseViewModel, not a rewrite: `savedStateHandle: SavedStateHandle? = null` plus a `saved(key) { ... }` helper built on lifecycle 2.9's `SavedStateHandle.saved()`/`getMutableStateFlow`, so a ViewModel opts a few fields in (`private var query by saved("query") { "" }`). Demonstrate it in two places — the login form and the search query — and have Koin's `viewModelOf` supply the handle (it already resolves it when declared). Keep route keys as they are. One line in CLAUDE.md's MVI section saying which state goes where.

Evidence: `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:59-61`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:83-89`; `service/core/ui/build.gradle.kts:23`; `feature/auth/presentation/src/main/kotlin/com/example/androidproject1/feature/auth/presentation/login/LoginViewModel.kt:16-22`; `feature/catalog/presentation/src/main/kotlin/com/example/androidproject1/feature/catalog/presentation/search/ProductSearchViewModel.kt:37-39`
### P4 · About 450 lines of service/core API have zero callers: Outcome flow combinators, recover, executeAsFlow, 7 of 8 Formats roles, CredentialsError, displayMessage

**medium · useless · effort S · confidence 0.9**

Counted across feature/ and app/ main sources: `combineOutcomes` 0, `chainOutcomes` 0 (OutcomeFlows.kt, 60 lines + 4 tests), `Outcome.recover` 0, `flatMap` 0 (`map` is used once, ProductSearchViewModel:69), `executeAsFlow` 0. `Formats` exposes 8 roles; only `money` is called (6 sites) — `moneyShort`, `weight`, `quantity`, `percent`, `time`, `date`, `duration` have 0 callers yet CLAUDE.md lists all eight as the API to build on, and FormatsTest covers them. `DomainError.displayMessage` is a raw `String` on a domain object (DomainError.kt:9-13) — never set by HttpErrorMapper or any feature (0 uses), but read as a user-facing message at BaseViewModel.kt:398, which would show an unlocalized server string if anyone ever did set it. `CredentialsError` is never constructed; `UnauthorizedError`/`NotFoundError`/`BadRequestError` are produced by HttpErrorMapper but no feature ever branches on them (`onError` is used twice, both ignore the type). **Proposal.** Delete OutcomeFlows.kt and its tests, `recover`, `executeAsFlow`, `CredentialsError`, and the `displayMessage` property (a localized message belongs in UiText in the presentation layer, mapped from the error type — which is what `commonErrorMessage` already does). Trim Formats to the roles the sample uses plus `date`/`time` if you want them demonstrated, and add one call site per role you keep so the goldens show them; the rest come back the day a screen needs them, in ten lines. Prune the CLAUDE.md API table to match. Net: roughly 450 fewer main lines and ~25 fewer tests to maintain in the part of the repo a newcomer reads first.

### P5 · No connectivity signal: offline is only discovered after a call fails

**medium · missing-standard · effort S · confidence 0.6**

`ConnectivityManager`/`NetworkCallback` appear in 0 files. The template has an offline-first repository, a `core_error_no_connection` string, a stale-content snackbar (ProductsViewModel:57-62) and a debug-menu offline toggle, but nothing that can tell a screen it is offline before it tries. NiA ships `NetworkMonitor: Flow<Boolean>` in core/data with a `ConnectivityManagerNetworkMonitor` implementation and surfaces it as one snackbar at the app root; Google's offline-first guide treats it as baseline. The backlog parks WorkManager and Paging behind Q8 (no real API yet) — reasonable — but a connectivity monitor is ~40 lines, has no API dependency, and is what turns `cached()`'s stale-then-fail sequence into a deliberate 'You're offline — showing saved items' rather than a retry button the user cannot act on.

**Proposal.** Add `NetworkMonitor` (interface in :service:core:domain, `ConnectivityManagerNetworkMonitor` in :service:core:data via `callbackFlow`, a `FakeNetworkMonitor` test fixture), bind it in coreModule, and observe it once in AppNavHost/AppScaffold to show a single offline banner. Optionally let `BaseViewModel.handleError` skip the NetworkError alert when the monitor already says offline. Keep it out of feature ViewModels.

## Looks heavy but is justified
- Outcome instead of kotlin.Result: kotlin.Result is discouraged as a domain return type and gives no typed error; NiA wraps in its own sealed Result too. Outcome.kt itself is 53 lines and the map/CancellationException handling is right — only the combinators around it are dead.
- DomainError as an Exception subclass: it lets a data source `throw` and BaseRepository map once (BaseRepository.kt:130-131, HttpErrorMapper.kt:30-54) instead of every source returning Outcome by hand; the seven-class hierarchy is small and matches HTTP reality.
- Buffered Channels for navigation/command (BaseViewModel.kt:91-98) and the reference-counted overlay (BaseViewModel.kt:184-194): the first fixes real event loss below STARTED, the second is exercised by ProductDetail's concurrent load+observe; both are tested.
- ErrorDisplay.Inline retry keyed by content id (BaseViewModel.kt:103-108, 221-235): ProductSearchViewModel runs two inline loads on one screen and the test at BaseViewModelTest.kt:226 shows why a single slot would retry the wrong one.
- Form/FieldState/Validator (124 lines): used by Login, SignUp and Profile; the touched-vs-valid split is the standard form model and there is no first-party library for it.
- NavResultStore: Navigation 3 has no previousBackStackEntry; the cart↔picker round trip proves it, it is a rememberSaveable so it survives process death, and it is 100 lines.
- The permission package (5 files, 3 call sites): Accompanist Permissions is deprecated, the four-case status with canAskAgain is what every real permission screen needs, and re-reading on resume is the part hand-written code forgets.
- Aead/AesGcmAead/KeystoreAead and EncryptedDataStoreProvider: security-crypto is deprecated, the session is the one value worth encrypting, and the logic is JVM-tested.
- core/di Koin.kt and KoinGraphTest: one list, one registration point, debug-only modules kept out of prod so R8 can drop them, and the graph verified in the builds that start it. Nothing to change.
- The service/ portability rule itself: the grep finds no leak, doctor enforces the feature-import half, and the JVM domain module enforces the android-free half at compile time. The cost is the :core:ui re-export and the un-themed shell (problem 2), not the rule.

## Questions only the owner can answer
- Will service/ ever be copied into a second project? If not within Plan 5, the portability rule is paying for the :core:ui → :service:core:ui re-export dance and the un-themed shell without a consumer; if yes, the shell-slot design in problem 2 is what makes the copy usable with the new project's theme.
- Should `initialState` remain nullable at all? Making State non-null and moving 'cannot render yet' into ContentState.Loading changes the template contract every generated screen starts from (TemplateArgsViewModel passes null today), so it is a decision to take before create_screen.py is touched.
- Is the connectivity monitor worth adding while everything is a MockEngine fixture (Q8)? It is small and independent of an API, but its only visible payoff is the offline banner and the debug-menu toggle would have to drive it too.
