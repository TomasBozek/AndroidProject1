**A. Date picker diagnosis**

Cause (two independent ones, both in how the picker is hosted, not in the picker):

1. Width. `AppDateField.kt:85-88` puts Material's `DatePicker` inside `AppDialog`. `AppDialog.kt:37` calls `Dialog(onDismissRequest = onDismiss)` with default `DialogProperties`, i.e. `usePlatformDefaultWidth = true`, and `AppDialog.kt:39-43` wraps content in `widthIn(max = 440.dp)` + `padding(AppTheme.spacing.inset.xl)` = 24 dp per side (`core/ui/.../theme/Spacing.kt:19,32`). Material's `DatePicker` demands `sizeIn(minWidth = 360.dp)` (material3 1.4.0 sources, `commonMain/androidx/compose/material3/DatePicker.kt:1356`, `DatePickerModalTokens.kt:28`; BOM 2026.08.00 resolves material3 to 1.4.0 per the cached compose-bom pom). So the card needs 360 + 48 = 408 dp inside a platform-width dialog window on a 360–411 dp phone: the right weekday column and the card's right edge are cut, and the Column simply overflows the window. Material's own `DatePickerDialog` exists precisely for this: it defaults `usePlatformDefaultWidth = false` (`DatePickerDialog.kt:59`) and uses `requiredWidth(360.dp)` with no horizontal inset (`DatePickerDialog.android.kt:83`).
2. Height. The `AppDialog` Column has no height cap and no scroll. Title + two `stack.md` gaps + picker (120 dp header + month bar + 7 rows) + button row + 48 dp padding is roughly 680 dp at font scale 1.0, more at 1.5 (the "Selected date" headline and title wrap), and a phone in landscape is ~360–410 dp tall, so Cancel/Choose are pushed below the window. Material caps at `heightIn(max = 568.dp)` and gives the content `weight(1f, fill = false)` so the buttons stay on screen (`DatePickerDialog.android.kt:84,96`). `AppTimeField` (`AppDateField.kt:146-149`) has the same landscape problem (256 dp dial + selectors + chrome).

Proof: none of the goldens can show it. `AppDateFieldKt.Preview.{Light,Dark,Large_font}.png` render only the closed field (looked at Large_font: four fields, no clipping). A `Dialog` is a separate window and the Roborazzi compose capture (`core/ui/.../screenshot/PreviewScreenshotTest.kt`, `captureRoboImage` on the preview) never sees it; `AppDialog.kt:97` says so in its own preview comment. Gallery goldens show the catalog list, not an open picker. Reproduce in the running app: Settings → Components → AppDateField on a 360 dp device, or any phone in landscape. Note the component is used by nothing but `GalleryCatalog.kt:734-749`.

Recommended fix (one option): in `AppDateField.kt:85-105` replace `AppDialog(... content = { DatePicker(state) } ...)` with Material's `DatePickerDialog(onDismissRequest = { open = false }, confirmButton = { AppButton("Choose", ...) }, dismissButton = { AppButton("Cancel", ..., kind = Ghost) }, shape = AppTheme.shapes.xl, colors = DatePickerDefaults.colors(containerColor = AppTheme.colors.surfaceRaised)) { DatePicker(state, modifier = Modifier.verticalScroll(rememberScrollState())) }`. The `verticalScroll` is the standard landscape workaround so the grid scrolls inside the 568 dp cap instead of clipping. Drop the `title`; the picker draws its own headline. Do the same for `AppTimeField` with a plain `Dialog(properties = DialogProperties(usePlatformDefaultWidth = false))` + scrollable content (1.4.0 has no stable `TimePickerDialog`). Goldens to re-record: none; the picker was never in one. If a golden is wanted, add one Roborazzi `captureScreenRoboImage()` test that opens the picker (that API captures dialog windows).

Alternatives: (b) harden `AppDialog` itself: `DialogProperties(usePlatformDefaultWidth = false)`, outer margin instead of inner horizontal padding, content in `Box(Modifier.weight(1f, fill = false).verticalScroll(...))` with title and actions outside the scroll. Worth doing anyway as a separate item because it fixes every future long-message or form dialog, but it still leaves 24 dp of padding around a 360 dp picker, so it is not the date fix on its own. (c) `DisplayMode.Input` as the initial mode: fits everywhere but contradicts the component's own contract ("never a text field", `AppDateField.kt:43`). Not recommended.

Other clipping: inspected the Large_font goldens of AppDialog, AppSheet, AppMenu, AppSelect, AppTooltip, AppToast, AppBottomNav, AppTabs, AppSegmented, AppTopBar, AppToolbar, AppStepper. Nothing visible is clipped, but AppDialog, AppSheet, AppMenu, AppSelect and AppTooltip goldens show only the trigger or the inline text (the overlay is a separate window), so overflow in any of them is invisible to the suite in exactly the way the date picker was.

**B. Retrospective**

Clear winners, leave alone: convention plugins + version catalog (`build-logic/` is 699 lines; module files are 6 lines, e.g. `feature/cart/presentation/build.gradle.kts`); AppTheme roles with no `material3` in features; `Screen()`/`UiState` envelope and `execute`/`observe`; a directory per screen (D34); find-by-testTag; tag-driven versioning and no vendor SDKs; `KoinGraphTest`; Roborazzi over CPST; Maestro weekly rather than per PR. The screen tests are real tests, not ceremony (`HomeScreenTest.kt:48-80` covers the empty branch), keep the two-per-screen rule.

Problems, ranked by impact:

1. The screenshot suite is mis-sized and blind where it matters. 349 goldens / 11 MB; every golden is a full 400x900 dp frame (`PreviewScreenshotTest.kt` `qualifiers = "w400dp-h900dp-xhdpi"`, 800x1800 px even for a badge, ~90% blank); 5 variants per screen and 3 per component; and no overlay is captured, so the suite could not catch the one visual bug the owner reported. Proposal: components get one light golden at content size (dark only where colour roles differ); screens get Phone + Dark + Large font, with Narrow phone/Tablet only on screens that actually have adaptive layouts; one screen-capture test for the popup components. Target ~120 goldens, ~3 MB. The 11 near-identical `PreviewScreenshotTest.kt` copies (diff is the package string, lines 1 and 92) are a D35 consequence; acceptable.

2. 27 of 47 `:core:ui` components are used by nothing except the 896-line `GalleryCatalog.kt`. Each costs 3 goldens (81 total), a gallery entry, a doctor check and maintenance; the reported bug is in one of them. Proposal: delete the unused 27 (they stay in git and in the KSD source), keep the gallery for the 20 in use. CLAUDE.md already states the rule: a component is added when a screen needs it.

3. Four Gradle modules per feature is the 2026 outlier. 56 modules; the 10 `di` modules total 257 lines (`feature/home/di` is 13 lines) and three features have no data at all; `:service:core:*` doubles `:core:*` with a package/namespace mismatch that needs its own gotcha. NIA and the architecture guide use one module per feature (UI + VM) and shared data modules. Proposal: two per feature, `:feature:x` (presentation + its Koin module) and `:feature:x:data` (domain interfaces + repositories + sources), keeping the `Default*` import rule. Roughly halves the module count. It is the one restructure worth its price, and the price is real (create/delete_feature, doctor's layer checks, settings helpers all change), so decide it before Plan 5 adds features, and let the build-timing agent's numbers confirm it.

4. The Python enforcement layer is 38% the size of the product. 7,053 lines of Python vs 18.5k Kotlin; `doctor.py` 1,256 lines, 30 checks, 19 s per run, plus a pre-commit hook. Several checks are doc-sync or one-off sanity, not architecture: "every feature is listed in CLAUDE.md's module tree" (`doctor.py:354`), "no foreign project identifiers" (`:748`), the CLAUDE.md-tree check, and the plurals check. Proposal: cut doctor to the checks that have bitten (registrations, layer directions, service portability, screen unit, resource prefixes), make it one filesystem pass, run it in CI only (drop `install_hooks.py`, D25 already says nothing enforces locally). Drop `delete_feature.py` (216 lines; `git rm` + doctor names the five places) and `export_service.py` (479 lines; zero consumers so far). Keep `init_project`, `create_feature`, `create_screen`, `create_component`: those are the template's actual value.

5. CLAUDE.md at 983 lines is loaded into every turn and duplicates `scripts/README.md`, `--help`, `.claude/commands/*` and PLAN-DETAIL. "Scaffolding scripts" alone is 150 lines (713-863); Crash reporting and Analytics carry vendor code samples. Proposal: ≤ 250 lines of rules, commands and pointers; the rest to `docs/ARCHITECTURE.md` and the existing command files. `docs/PLAN-WORKERS.md` (349 lines, "kept as the record") breaks the owner's own docs rule; delete it.

6. Overlay components are the design system's weakest layer and the date picker is the symptom, not the cause. `AppDialog.kt:37-43` is a platform-width `Dialog` with no height cap or scroll; `AppSheet`, `AppMenu`, `AppTooltip` are similarly uncaptured. Proposal: the AppDialog hardening from A(b) as one item, with a screen-capture golden per overlay component.

7. Mandatory Czech for every string in a template. Every new sample string needs a hand-written translation with four plural forms before doctor passes (`doctor.py:1133,1175`). For a template that is a tax on every feature; NIA ships none. Proposal: keep the mechanism (`TRANSLATED_LOCALES`) and demonstrate it on one feature; make a missing translation a doctor warning, and an error only once `init_project` declares the project's real locales. Stated as opinion; the owner may want it.

Fine as is, no action: CI job layout (doctor + scripts, ktlint, build, roborazzi, kover, weekly Maestro/generators); `BaseViewModel` at 452 lines is at the upper end but every piece is used; `feature/template` being compiled; tag-based release.
