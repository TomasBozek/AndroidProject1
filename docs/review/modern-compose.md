Context that decides most verdicts: the KSD design system hand-draws nearly everything. Only five of 47 :core:ui components touch a Material widget (AppDateField, AppSheet, AppSlider, AppMenu, AppSpinner/AppButton's CircularProgressIndicator; core/ui/.../component/*.kt imports). AppSegmented, AppTooltip, AppBadge, AppToolbar, AppBottomActionBar, AppTopBar, AppProgress are Row/Box drawings with keySurface elevation (AppSegmented.kt:40-71, AppTooltip.kt:20-32, AppTopBar.kt:36). A Material component "replacing" one of these would change the look, which is the design system's whole point.

RANKED LIST (adopt now first)

1. TextFieldState-based text fields — foundation 1.12.0, STABLE. Improves AppTextField (AppTextField.kt:56-58,100-107 still `value/onValueChange` + PasswordVisualTransformation) and AppSearchField (AppSearchField.kt:38-40,66). This is Google's recommended text API since 1.7; it fixes the classic lost-keystroke race when the ViewModel round-trips every character, gives InputTransformation for `numeric`, and BasicSecureTextField replaces PasswordVisualTransformation. Effort M (the state moves from `String` in XState to a TextFieldState owned by the ViewModel — LoginState.email/password, ProductsViewModel search; tests find the field the same way). Risk: low; the template rule "state is a data class the ViewModel copies" needs one written exception for TextFieldState, which is mutable by design. Showcase: the login screen. VERDICT: adopt now — it is the one item on this list that is both stable and an architectural correction.

2. Autofill on login — ui 1.12.0, STABLE. `Modifier.semantics { contentType = ContentType.EmailAddress / Password }` on the two fields in LoginScreen.kt:40-58; grep finds no `contentType` anywhere but the network module. Pairs naturally with 1 (BasicSecureTextField + autofill is the reference combination). Effort S. Risk none. Showcase: sign-in fills from the password manager. VERDICT: adopt now, together with 1.

3. PullToRefreshBox — material3 1.4.0, STABLE, not used anywhere (0 hits). The catalog already has the `cached`-then-refresh pattern (ProductsViewModel.kt:36-49, `catalog_stale`) but no user-triggered refresh; a Refresh event + `AppRefreshList` wrapper is the natural home. Effort S–M (new :core:ui component via create_component.py, indicator recoloured via AppTheme). Risk: the default indicator is Material-looking; the API takes a custom indicator slot. Showcase: Products list. VERDICT: adopt now — the most common list gesture in a product app and the template has no answer for it.

4. PredictiveBackHandler — activity-compose 1.13.0, STABLE. NavDisplay already does predictive pop by default (AppNavHost.kt:201-203); what is missing is a predictive-aware *in-screen* back for AppSheet and a dirty-form confirm (0 hits for BackHandler or PredictiveBackHandler). Effort S. Risk none on minSdk 29 (API 33+ gets the gesture, below it is a plain back). Showcase: an unsaved-changes dialog on Profile edit. VERDICT: adopt now, small.

5. SharedTransitionLayout with Navigation 3 — animation 1.12.0, EXPERIMENTAL (ExperimentalSharedTransitionApi still present). Product row → product detail image is the textbook case and the catalog has both screens. Nav 3 exposes `LocalNavAnimatedContentScope`, so it composes; but the SharedTransitionScope has to live in AppNavHost and be reached by feature presentation modules through a CompositionLocal in :core:ui, and Roborazzi's single-frame capture (PreviewScreenshotTest) does not exercise it. Effort M. Risk: experimental churn and one more thing every screen preview must tolerate. VERDICT: showcase only — one pair of screens, behind a helper in :core:ui, not a rule.

6. Modifier.dropShadow / innerShadow — ui 1.12.0, STABLE. Not a replacement: keySurface (Elevation.kt) deliberately uses a hard edge rather than blur and CLAUDE.md forbids Modifier.shadow. Where it earns a place is AppScrollShadow and the sheet scrim, which currently fake a gradient. Effort S. VERDICT: adopt opportunistically when those two components are touched; do not add a rule.

7. TextAutoSize — foundation 1.12.0, STABLE. One `autoSize = TextAutoSize.StepBased()` parameter on AppText for the numeric role (prices in cart tiles, the KPI figures on Home) — the Czech translations (feat.9) are the concrete reason, since strings got longer. Effort S. VERDICT: adopt now as a parameter on AppText, no new component.

8. Material 3 Expressive family (ButtonGroup, ToggleButton, SplitButton, FloatingToolbar, LoadingIndicator, WavyProgressIndicator, FAB menu, MaterialShapes morphing via graphics-shapes 1.1.0) — material3 1.5.0-alpha17 only, EXPERIMENTAL (@ExperimentalMaterial3ExpressiveApi), NOT in this BOM. Effort L (pin material3 off the BOM, MaterialExpressiveTheme, motionScheme, plus a redesign of components the KSD system already draws differently). VERDICT: skip for Plan 5; see D10 below.

SKIP AND WHY
- SearchBar (material3, experimental) vs AppSearchField: SearchBar is a full-screen expanding surface with suggestions; the catalog needs an inline filter field, which AppSearchField already is. Keep it; migrate its internals to TextFieldState (item 1).
- SegmentedButton / ButtonGroup vs AppSegmented: SegmentedButton is stable in 1.4.0 but AppSegmented.kt:40-71 is a deliberate KSD drawing (sunken surface, hard border). Swapping it changes the design for no functional gain; ButtonGroup is 1.5-alpha only.
- Carousel (material3, experimental) vs AppPager: the multi-browse carousel is a media-gallery idiom; the sample app has one image per product. AppPager on stable HorizontalPager covers onboarding. Revisit only if a hero-image feature arrives.
- Tooltip (material3, experimental) vs AppTooltip: AppTooltip.kt:16 already documents the reason — no hover on touch, so the tooltip is a static label; TooltipBox adds long-press plumbing the design does not want.
- LoadingIndicator / WavyProgressIndicator vs AppProgress/AppSpinner: 1.5-alpha only, and AppProgress.kt draws its own bar in the KSD style; AppSpinner's CircularProgressIndicator is already the stable one.
- FloatingToolbar vs AppToolbar/AppBottomActionBar: 1.5-alpha only; AppBottomActionBar is a Row on a keySurface, which is the design.
- Medium/LargeFlexibleTopAppBar + TopAppBarScrollBehavior: experimental, and AppTopBar.kt:36 is a fixed-height Row by design; collapsing headers are not in the KSD system.
- Credential Manager (androidx.credentials): not in the cache, not in the graph. The sample AuthService is a boolean fake (CLAUDE.md Crash reporting section: "the sample AuthService exposes only a boolean"), so there is no backend to hand a credential to; adding the library and a Google client id to a template forces a vendor choice on every project, which D27's spirit is against. Leave a one-paragraph note in PLAN-DETAIL on where it would plug in (AuthRepository) and stop there.
- graphics-shapes morphing: the library is on the classpath transitively (1.1.0), but the only consumer worth showcasing is Expressive's MaterialShapes / loading indicator, which is 1.5-alpha. Skip with Expressive.
- retain / rememberSerializable: not present in runtime 1.12.0 / savedstate-compose 1.5.0 on this machine; nothing to adopt yet.

MATERIAL 3 EXPRESSIVE AND D10
What Expressive would change: MaterialExpressiveTheme with a MotionScheme (spring-based, replacing Motion.kt's hand-tuned tweens at Motion.kt:18-27), the new shape scale and MaterialShapes, and the component family listed under item 8. In THIS template it would change almost nothing the user sees, because only five App* components delegate to Material at all; every button, segmented control, toolbar, badge and progress bar is a KSD drawing with keySurface elevation. The system would have to be redesigned to be Expressive, not re-themed. On top of that, the jar shows the components are not in the stable 1.4.0 the BOM pins, so adopting them means leaving the BOM for a 1.5 alpha in a template that Renovate keeps on stable (renovate.json skips pre-releases per CLAUDE.md Project section).
Verdict on D10: keep it, but reword the reason. Today's line ("No, standard M3", docs/PLAN.md:88) suggests a taste choice; the evidence is stronger: the design system does not render through Material components, and the Expressive set is alpha-only at this BOM. Add a trigger for reopening: material3 1.5.0 stable landing in a BOM, plus a decision to make the KSD system Material-shaped. Until both hold, Expressive is a gallery curiosity, not a template feature.

SUGGESTED PLAN 5 ITEM (one, not eight)
"Modern text input and list refresh": TextFieldState in AppTextField/AppSearchField, BasicSecureTextField + autofill contentType on Login, PullToRefreshBox as AppRefreshList on Products, PredictiveBackHandler for the unsaved-edit confirm, TextAutoSize on the numeric AppText role. All stable in the resolved BOM, all touch screens that already exist, no dependency added. Shared elements and dropShadow ride along as opportunistic showcase work if a screen they fit is being edited anyway.
