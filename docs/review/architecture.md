# Reusable architecture: service/core/{domain,data,ui}, core/di
<!-- Generated 2026-09-10 from the review agents' saved output. Evidence is path:line at commit 4e0d2fc. Not edited by hand; the ranked summary is ../REVIEW.md. -->

## Summary
The shape is right and close to what Now in Android ships: a sealed result type, a thin repository base, a single Screen() collector, vendor-free seams for crash reporting and analytics, and a DI graph that is verified by a test. The 2,890 main lines of service/core + core/di are backed by 118 JVM tests and every repository and ViewModel in the sample app actually goes through them. The problems are concentrated in one file: BaseViewModel's defaults are the opposite of what every screen wants (the blocking overlay is switched off at ~20 of 28 call sites, each with a comment explaining why), its nullable-data envelope drops updates silently, and about 150 lines of its API plus the Outcome flow combinators are exercised only by their own tests. Two standard things a product app needs on day one are missing — SavedStateHandle for transient UI state and a connectivity signal — and the service/ portability split forces the framework's own loading/error/empty/permission chrome to be drawn outside the design system, which is the one place the app breaks its own "never draw" rule.

## Problems (ranked by the reviewer)
### P1 · BaseViewModel's defaults are the opposite of what every screen wants

**high · over-engineered · effort M · confidence 0.9**

execute() has 8 parameters and observe() has 9. The default `loading` shows a full-screen scrim that swallows touches (LoadingOverlay.kt:26-28). Across the 15 sample ViewModels there are 28 execute/observe call sites and 20 of them pass `loading = {}` — Cart 4/4, ProductDetail 3/3, ProductSearch 3/3, Home 2/2, Settings 3/4, Onboarding, DevMenu, ProductPicker — and most carry a comment justifying the override ("a heart is not worth an overlay", "an overlay over an empty Home is worse than the empty section"). Only 3 call sites want the overlay (Login, SignUp, Profile.setAvatar). `onData` is a mandatory trailing parameter, so 6 call sites pass `onData = {}` and CartViewModel wraps execute in its own `write()` helper (line 128) to hide it. The Inline-retry closure is copy-pasted between execute (220-243) and observe (290-311). This is the one file a new developer must understand to write any screen, and it teaches a blocking-modal pattern that Material guidance and Now in Android stopped using years ago — the sample app itself has voted against it 20 times.

**Proposal.** Flip the defaults and shrink the signature: `execute(action)` = no overlay, error → alert, `onData` optional; `load(action)` = ErrorDisplay.Inline with retry, for the call that loads a screen; overlay becomes opt-in (`blocking = loadingMessage`). Drop the `scope` parameter (0 usages). Extract the retry bookkeeping into one private helper shared by execute/observe. Update feature/template so generated screens get the new shape. Target: BaseViewModel under 300 lines and no `loading = {}` anywhere in a feature.

Evidence: `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:208`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:276`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:220`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:290`; `feature/cart/presentation/src/main/kotlin/com/example/androidproject1/feature/cart/presentation/cart/CartViewModel.kt:82`; `feature/home/presentation/src/main/kotlin/com/example/androidproject1/feature/home/presentation/home/HomeViewModel.kt:52`; `feature/settings/presentation/src/main/kotlin/com/example/androidproject1/feature/settings/presentation/settings/SettingsViewModel.kt:54`; `feature/profile/presentation/src/main/kotlin/com/example/androidproject1/feature/profile/presentation/profile/ProfileViewModel.kt:26`
### P2 · The nullable-data envelope drops updates silently and can render a blank screen

**high · bug · effort M · confidence 0.75**

`state: StateFlow<UiState<State?>>` exists so `initialState = null` can start the overlay. The costs: `updateData` is a no-op while data is null (UiState.kt:36) and `state.data?.copy(...)` in features is the same silent drop; Screen() draws nothing at all when data == null and content == null (Screen.kt:63), so `initialState = null` + `ErrorDisplay.Silent` is a permanently blank screen with no overlay. Concrete case: ProductDetailViewModel starts `load()` and `observeFavourite()` in init (lines 34-37). Both read local storage, so ordering is not guaranteed; if the favourite emission lands first it is dropped by `state.data?.copy` (line 67-69), and `load()` then writes `ProductDetailState(product)` whose `isFavourite` defaults to false (ProductDetailState.kt:9) — the heart is wrong until the row changes again. ProductDetailViewModelTest does not cover that ordering. Google's guide and Now in Android make the screen state non-null and put `isLoading`/`Loading` inside the feature's own state class; there is no null path to forget.

**Proposal.** Make `initialState: State` required (non-null) and `UiState<State>` non-nullable; delete `updateData`'s null branch. The three ViewModels that pass null today (Products, Categories, ProductDetail) get a `loading = true` / empty-list field in their own state, which is what their screens want to draw anyway (a skeleton or an empty list rather than a scrim over nothing). Add the favourite-before-product ordering as a JVM test while touching ProductDetailViewModel.

Evidence: `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/state/UiState.kt:34`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/component/Screen.kt:63`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:83`; `feature/catalog/presentation/src/main/kotlin/com/example/androidproject1/feature/catalog/presentation/productdetail/ProductDetailViewModel.kt:34`; `feature/catalog/presentation/src/main/kotlin/com/example/androidproject1/feature/catalog/presentation/productdetail/ProductDetailViewModel.kt:67`; `feature/catalog/presentation/src/main/kotlin/com/example/androidproject1/feature/catalog/presentation/productdetail/ProductDetailState.kt:9`
### P3 · No SavedStateHandle: transient UI state is lost on process death, while the dependency is shipped unused

**medium · missing-standard · effort M · confidence 0.85**

`lifecycle-viewmodel-savedstate` is `api`'d from :service:core:ui and `SavedStateHandle` appears in zero main-source files (one test mention). The back stack and route keys survive process death (Nav3 + rememberNavBackStack, and the BaseViewModel KDoc at line 59 explains why the key needs no SavedStateHandle) — but everything typed into a form does not: LoginState/SignUpState/ProfileState field values and ProductSearchViewModel's `query` (a plain MutableStateFlow) live only in the ViewModel. Google's guide to UI state is explicit that simple transient UI state (text input, a search query, a selected tab) belongs in SavedStateHandle, and Now in Android does this for the search query. A template that already went to the trouble of a saveable NavResultStore (NavResultStore.kt:65) and a saveable `hasRequested` in rememberPermissionRequest (PermissionRequest.kt:61) but not for the text a user typed has the priority backwards.

**Proposal.** Give BaseViewModel an optional `SavedStateHandle` (Koin's `viewModelOf` injects it automatically) and a one-line helper — `saved(key, default)` backed by `handle.getStateFlow` — that the form-bearing ViewModels use for field values and the search query. Wire it into feature/template so generated screens carry it. Either use the dependency or remove the `api(...)` line.

Evidence: `service/core/ui/build.gradle.kts:24`; `service/core/ui/src/main/kotlin/com/example/androidproject1/core/ui/viewmodel/BaseViewModel.kt:59`; `feature/catalog/presentation/src/main/kotlin/com/example/androidproject1/feature/catalog/presentation/search/ProductSearchViewModel.kt:39`; `feature/auth/presentation/src/main/kotlin/com/example/androidproject1/feature/auth/presentation/login/LoginViewModel.kt:18`; `feature/profile/presentation/src/main/kotlin/com/example/androidproject1/feature/profile/presentation/profile/ProfileViewModel.kt:45`
### P4 · The framework's own chrome (loading, error, empty, alert, permission rationale) is drawn outside the design system

**medium · inconsistent · effort M · confidence 0.85**

CLAUDE.md's hardest UI rule is "a feature composes components; it never draws" — no material3, no `.dp`, no MaterialTheme.colorScheme. The four composables that render the states users see most (every error page, every empty page, every loading overlay, every confirm dialog, every permission rationale) break all three: ContentMessage uses `32.dp`/`12.dp`/`8.dp` and `MaterialTheme.typography`, LoadingOverlay uses a raw `CircularProgressIndicator` and `16.dp`, PermissionRationaleContent uses material3 `Button` and `32.dp`/`12.dp`, StateAlertDialog is material3 `AlertDialog`. That is 17 `.dp`/`MaterialTheme.` occurrences in a module that the doctor's design-system check does not cover. The cause is structural: :service:core:ui cannot depend on :core:ui, so it has no AppTheme, no AppButton, no AppText. The result is that a re-brand — the thing the three-layer design system exists to make a one-file change — leaves the error and empty states looking like stock Material.

**Proposal.** Keep the contracts (UiState, ContentState, AlertState, LoadingState, PermissionRationale) in service/core/ui and move the rendering to :core:ui, where it can use the design system: either Screen() takes the four renderers as a `ScreenChrome` composition local that :core:ui provides (AppNavHost already provides Analytics and NavResultStore in the same place), or Screen() itself moves to :core:ui since it is the only consumer of the four. Add the four to GalleryCatalog so they get screenshot goldens like every other component.

### P6 · No connectivity signal: offline is only discovered after a call fails

**medium · missing-standard · effort S · confidence 0.8**

The only knowledge of the network the UI layer has is `NetworkError` → the `core_error_no_connection` string after a request has already failed. There is no `isOnline: Flow<Boolean>` anywhere (grep for connectivity/NetworkMonitor/isOnline across the repo returns nothing outside docs), and the dev menu's offline toggle is "a fixture told to fail, not a network drop" (PLAN-DETAIL.md:91). Now in Android ships `NetworkMonitor` in core/data with a ConnectivityManager implementation and shows a persistent "You are not connected" snackbar from the app scaffold; every product app with a cache-first repository (which `BaseRepository.cached()` makes the default shape here) needs it on day one so the user knows why the refresh did not happen and so a ViewModel can skip a doomed call.

**Proposal.** Add `NetworkMonitor { val isOnline: Flow<Boolean> }` to service/core/domain, a `ConnectivityManager.registerDefaultNetworkCallback` implementation in service/core/data (about 40 lines, bound in coreModule), and one offline banner rendered once in AppNavHost's scaffold rather than per screen. Make the dev menu's offline toggle override it so the fixture story becomes real.

### P7 · The service/ portability split costs more than a template gets back from it

**medium · over-engineered · effort L · confidence 0.6**

The claim is real at the dependency level: no service/ file references :core:*, :feature:* or :app (grep clean; doctor.py checks it at lines 126 and 520), the domain module is Kotlin/JVM so the compiler enforces the android-free rule. But the price is paid every day and the benefit is exercised only by export_service.py. Costs: (1) split packages — `com.example.androidproject1.core.ui.component` is declared in 47 files of :core:ui and 4 files of :service:core:ui, and `core.ui.*` generally spans two modules, so the IDE cannot tell you which module a symbol lives in and JPMS/R8 tooling treats it as a smell; (2) the `...service.core.ui.R` vs `...core.ui.R` import that every file in the module has to spell (BaseViewModel.kt:22); (3) the `core_` resource prefix and its two doctor checks; (4) the chrome problem above, which exists only because service cannot see the theme; (5) `Logger`/`AndroidLogger` split across two modules and the `isDebug` parameter threaded through coreModule because service/ cannot read BuildConfig. A project in 2026 starts from this template via init_project.py; the case where someone copies service/ into a foreign project is the rare one, and Now in Android's flat `core:common / core:data / core:ui / core:designsystem` needs none of this apparatus.

**Proposal.** Decide, and put the decision in PLAN.md. Option A (recommended): fold :service:core:* into :core:*, drop export_service.py and the three portability doctor checks, keep the one rule that actually pays — a Kotlin/JVM domain module. Option B: keep the split but end the split packages by moving service/ code to `...service.core.*` packages, and fix the chrome via the slot in the previous finding. Either way, stop paying for both.

## Looks heavy but is justified
- Outcome as a sealed type rather than kotlin.Result: Result<T> forces Throwable-typed errors and swallows CancellationException in runCatching; Outcome.toFailure() (Outcome.kt:26) handles that once and Now in Android makes the same choice.
- The DomainError hierarchy (7 classes, 44 lines in DomainErrors.kt): only ServerError and NetworkError are branched on in the UI (BaseViewModel.kt:393, 421), but HttpErrorMapper produces all seven and the mapping table lives in one place; the classes are the price of never re-reading a status code in a repository.
- BaseRepository (137 lines): execute/observe/cached are all used by the sample repositories, cancellation is handled once, and cached()'s stale-then-error contract is what makes ProductsViewModel's keepStaleContent a three-line function.
- Formats/LocalFormats: 122 lines, used by 5 screen files in catalog and cart, replaced two divergent Price.kt copies, and money-in-minor-units with currency-derived scale is the correct model; the doctor check that bans NumberFormat in a feature is what keeps it the only copy.
- NavResultStore: used by the cart/picker round trip, saveable, consumed once. Navigation 3 genuinely has no previousBackStackEntry, so a 100-line store above the NavDisplay is the standard answer, not an invention.
- Form/FieldState/Validator: 124 lines, used by Login, SignUp and Profile. The touched flag is the one thing a hand-rolled boolean gets wrong, and validators as fun interfaces returning UiText keep it Context-free.
- The permission package: used by settings and profile through three entry points; wrapping rememberLauncherForActivityResult in 120 lines beats adding Accompanist-permissions, which is deprecated.
- Aead/AesGcmAead/KeystoreAead/EncryptedDataStoreProvider: about 130 lines replacing the deprecated security-crypto library, the logic JVM-tested, the Keystore fetch fifteen lines, and used for the one value that deserves it (the session).
- ErrorTracker/TrackingLogger and Analytics/ScreenViewEffect: vendor-free seams with real default implementations, wired by decoration so no constructor changes; setUser is actually called from MainViewModel.
- core/di Koin.kt and KoinGraphTest: 130 lines, a reason on every binding, the debug-only list split for R8, and a graph test with injectedParameters that the generators keep current.
- The 118 JVM tests under service/core (BaseViewModelTest 19, BaseRepositoryTest 15, OutcomeTest 14, FormTest 14, FormatsTest 12): proportionate to 2,890 main lines, no Robolectric except the permission package, and they are what makes refactoring the base safe.

## Questions only the owner can answer
- Is copy-portability of service/ into a foreign project still a goal now that every new project starts from init_project.py? The answer decides whether to fold :service:core:* into :core:* or to keep paying for the split packages and the off-system chrome.
- Do you want a blocking full-screen loading overlay to exist at all? The sample app switches it off at 20 of 28 call sites; if the answer is 'only for Login/SignUp/photo save', it should be opt-in and the envelope's `loading` field can go.
- Should `initialState = null` remain allowed? Removing it makes the state non-null (the Google/NiA shape) and closes the silent-drop path, at the cost of three ViewModels gaining a `loading` field in their own state.
- How much of the sample app's job is to demonstrate the base API? Deleting the unused combinators and whileSubscribed shrinks what a new developer must learn; keeping them means the sample features should exercise them or CLAUDE.md should stop listing them.
